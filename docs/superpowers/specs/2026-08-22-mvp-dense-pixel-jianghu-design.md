# 单主角 MVP：高密度俯视像素江湖美术规格

> 状态：方向已由用户于 2026-08-22 确认；本文件是进入实现计划前的冻结规格。
>
> 目标：把烟柳镇与客栈从“底图上叠角色”的原型，重做为角色、建筑、道具和可走空间统一的原创俯视像素试玩切片。

## 1. 设计依据与边界

本次参考《大侠立志传》的**可读性方法**：俯视像素空间内角色与环境同尺度、以功能道具建立生活密度、以道路/边缘/剪影传达可走性。不得复制其人物、服装、建筑布局、图标、界面、配色样本、截图或任何游戏资源。

当前 `Assets/Art/Environment/MVP/v2/` 的三张 `480×270` 整幅图层是上一轮的技术修复产物。它们把场景当成背景画布，无法表达真实的建筑层级、前景遮挡和物件关系；它们必须从两张 Demo 的运行时装配中退出，但可保留在 Git 历史中以便回溯。

本规格只涵盖以下单主角 MVP 内容：

- 固定男主 `player_male_swordsman` 与三个武器流派的外观层。
- `Demo_YanLiuTown` 的客栈门口、河岸战斗区及其连通路线。
- `Demo_Inn` 的入口、掌柜柜台、桌席、灶火、楼梯和北侧出口。
- 两名水匪、掌柜、荷包的 MVP 专用外观。

不涵盖其他 11 套主角、正式 97 角色、正式区域/室内基线、剧情扩写、UI 功能、ProjectSettings 改动或新增地图。MVP_01、QuestStageGate、存档 v5、三流派数值和已有碰撞/传送契约均保持不变。

## 2. 视觉目标与验收尺度

### 2.1 一致像素比例

- 内部渲染固定 `480×270`，Point 过滤、无压缩、无抗锯齿、PPU `16`。
- 保留既有 `16×16` 世界碰撞格；这是为了不破坏已验证的出生点、门、河岸和荷包可达性。
- 不采用上一轮口头提出的 `24×24` 碰撞格。改用 **16px 基础格 + 32/48/64px 多格模块**，在不改变玩法坐标的前提下提高建筑和道具的细节密度。
- 男主、掌柜和水匪使用 `48×48` 原创精灵（3×3 基础格），每帧以同一 PPU 导入；小型荷包为 `16×16`，灯笼/桌椅/木箱等为 `16×16` 或 `32×32`。
- 场景不允许再以任何 `480×270` 整幅 PNG 作为运行时背景。每个可见建筑、道路、水岸、道具或遮挡物都必须由持久小图块/多格模块在世界坐标中布置。

### 2.2 男主母版

男主为成年江湖游侠，三头身、上窄下宽、站姿稳定。必须在实际 1× 游戏画面中一眼读出五个识别点：深发束、靛蓝短披、米白内衫、朱砂腰绦、斜背或手持的钢剑。

- 四方向各自绘制，不得镜像。
- 制作 `idle`、`walk`、`attack` 三个 MVP 必需动作；idle 4 帧、walk 6 帧、attack 5 帧。攻击必须有蓄势、出招和收势，披风或衣摆至少有一帧后续动作。
- 流派只替换武器层：剑、拳套、飞镖袋/飞镖。脸、体态、衣服和角色身份不变；不能把流派当作三套角色。
- 角色在无遮挡地面上的实际可见高度不得低于 42 屏幕像素；角色脚底、投影和碰撞脚点必须对齐。

### 2.3 烟柳镇空间脚本

试玩镜头只服务于“客栈门口 → 河岸战斗 → 回客栈”的任务路线。

1. **客栈门口**：多格黛瓦屋檐、白灰墙、深木门框、招牌和一对暖灯构成地标；门口石路的材质、边缘和阴影须能一眼区分于屋基与水面。
2. **主路与水岸**：石路有至少三种非重复拼接变化；水面有深浅带、岸线、木桩和倒影，但不以均匀横线或大面积重复短线填满画面。
3. **河岸战斗区**：两名水匪处于平整的可战斗地面，周围放置船、系船桩、麻袋/货箱、灯柱等少量功能道具；荷包用金暖色和 1px 暗边与地面区分。
4. **建筑和遮挡**：至少一个屋檐/柳枝/招牌位于 Foreground，只遮边缘而不遮男主；环境层必须表现墙体、门、桥台等有体积的中景物。

### 2.4 客栈空间脚本

客栈不是一个棕色矩形。入口石阶、门厅木地板、柜台、桌席、灶火、楼梯和出口必须用不同的形状、材质和局部明度组成一个可走室内。

- 柜台与掌柜是第一个注意点：柜台轮廓、掌柜剪影、账本/酒坛和两盏暖灯构成主焦点。
- 入口到柜台、柜台到北出口有连续可读的地面路径；桌脚、梁柱和前景家具不得侵入该路径的碰撞格。
- 灶火和窗光为次级暖光，木板细节只在光区出现；暗处仍要用楼梯、墙柱或家具剪影解释空间，禁止以无信息纯黑填充。
- 入口门帘、桌角或梁柱可进入 Foreground，但总遮挡面积不超过画面 15%，且不遮角色脚点或交互对象。

## 3. 调色与像素语言

每个镜头使用一个共享、有限的色板；色彩职责不能混用。

| 组别 | 用途 | 限制 |
| --- | --- | --- |
| 墨青/蓝灰 | 外轮廓、深水、屋瓦阴影 | 只用于受遮挡边缘与结构下缘，不做全物体黑描边。 |
| 宣纸/灰白 | 墙面、衣物高光、石路亮面 | 只在受光面成簇出现，不能以平铺白块代替体积。 |
| 赭木/土棕 | 梁柱、柜台、船、木箱、地面暖暗部 | 同类物必须复用同一明暗阶。 |
| 青碧 | 水面、柳叶、远景植被 | 以大中小三种像素簇组织，避免随机散点。 |
| 朱砂/暖金 | 男主腰绦、灯笼、任务荷包、交互焦点 | 每个 480×270 镜头不超过可见像素的 5%，只用于焦点。 |

所有美术采用选择性描边、2–5px 像素簇和明确的受光/背光面；禁止抗锯齿、渐变滤镜、照片纹理、单像素噪点及不同来源的像素密度混合。

## 4. 技术架构

### 4.1 资源组织

新增的可编辑源与烘焙资产使用以下目录；每个 PNG 需要对应 `.meta`，使用稳定 snake_case 名称。

```text
Assets/ArtSource/MVP/dense_pixel/
  characters/hero_male/             # 48×48 源帧与武器层
  characters/actors/                # innkeeper、bandit_a、bandit_b、lost_pouch
  environment/town/tiles/           # 16×16 地面/水/岸线
  environment/town/modules/         # 32/48/64px 客栈、桥、船、码头、植被
  environment/inn/tiles/            # 地板、墙、阴影、暖光
  environment/inn/modules/          # 柜台、桌席、灶、楼梯、门帘
Assets/Art/MVP/dense_pixel/         # 导入到 Unity 的等价运行时输出
Assets/Resources/Art/MVP/dense_pixel/actors/
```

资源只能由确定性构建器或明确记录的原始手工像素源生成；不得从参考游戏提取、临摹轮廓或重打包外部资源。

### 4.2 场景装配

`PlaySceneAssembler.CreateMvpSceneLayers` 和两处 Demo 生成器改为从可组合模块创建世界对象：

```text
Ground       地面、水面、可走路面
Environment  墙体、桥、柜台、船、树、可交互道具
Character    男主、掌柜、水匪、荷包
Foreground   屋檐、柳枝、门帘、柜台前沿
```

每一个模块是带 `SpriteRenderer` 的持久资源对象，具有明确的世界坐标、pivot、sorting order 和可选碰撞。渲染排序继续符合 `Ground → Environment → Character → Foreground → UI`。禁止生成运行时 `Texture2D` 或 `Sprite.Create`；禁止在玩法场景挂整幅背景 `SpriteRenderer`。

碰撞沿用已有门、河岸、水匪、荷包和通路契约。视觉模块可以改变位置的观感，但不能让可走地面看起来被阻挡，或让不可走建筑看起来可穿过。

## 5. 流程、兼容性与错误处理

- 两张 Demo 均由现有编辑器生成命令重建；重复生成的资产顺序、名称和场景引用必须确定性一致。
- 场景缺失任何必需精灵时，编辑器生成必须抛出含资源路径的错误，而不是回退为颜色块或旧整幅图层。
- `MVP_01` 的任务阶段门、两名水匪、荷包、客栈掌柜、镇↔客栈传送、TransitionCarry 和三个流派功能不得改变语义。
- 主菜单武器预览沿用持久功能小图的行为；新角色武器层只作用于游戏内男主渲染，不改变存档字段或流派 ID。

## 6. 自动验证与人工门禁

### 6.1 必须新增/调整的自动测试

1. Python：验证模块资源尺寸只为 16/32/48/64px，主角帧为 48×48，四方向源哈希均不同，武器层为三个独立持久资源；验证不存在新 `480×270` MVP 运行时背景 PNG。
2. Python：验证烟柳镇和客栈模块清单含本规格中列出的可读地标，且 Ground/Environment/Foreground 均有实际资源。
3. EditMode：重建两个 Demo 后断言没有名为 `[MVP Ground]`、`[MVP Environment]` 或 `[MVP Foreground]` 的整幅背景层；断言场景模块均引用持久 Sprite，角色处于 Environment 和 Foreground 之间。
4. EditMode：验证关键世界位置的碰撞/可达性仍满足出生点→客栈门→河岸→荷包和客栈入口→掌柜→出口的既有 BFS 契约。
5. PlayMode：保留并复跑主菜单选流派、接取任务、两水匪、拾荷包、回掌柜和镇↔客栈往返的全链路测试。
6. 离屏截图：固定在真实 `480×270` 相机下生成“客栈门口、河岸、柜台”三张 1× PNG；测试只保证非黑帧、角色存在、HUD 和世界同帧，不能替代美术批准。

### 6.2 Gate V：人工视觉验收

仅当以下全部由用户在**未放大**的 `480×270` 真实截图或 Unity Game View 确认后，才可称完成：

1. 三张画面在一秒内能看出男主、当前目标/敌人、可走路线与主要地标。
2. 男主不是贴在背景上：脚点、投影、前景遮挡和光源与环境一致。
3. 烟柳镇是生活化水乡，客栈是有功能分区的室内；不存在大面积重复纹理、空白水面或纯色矩形占主体。
4. 视觉变更没有损坏 MVP_01 闭环、战斗、交互、场景往返或存档。

## 7. 交付顺序

1. **Gate H（男主母版）**：交付男主 48×48 四方向 `idle/walk/attack` 与三个武器层，先在空白/石路检视 1× 可读性。未获批准不得开始场景批量绘制。
2. **Gate T（烟柳镇）**：交付客栈门口与河岸的模块化试玩场景、实际任务通路和一张 1× 实拍。未获批准不得开始客栈替换。
3. **Gate I（客栈）**：交付柜台、桌席、灶火、楼梯、出口及完整往返链路的一张 1× 实拍。
4. **Gate V（最终试玩）**：执行完整自动测试、批处理编译与三流派人工试玩，并由用户通过 1× 视觉验收。

每一门只交付对应范围，不提前扩展其他区域、美术资产或玩法系统。
