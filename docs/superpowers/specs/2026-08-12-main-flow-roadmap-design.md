# 渊海录主流程与开发路线图设计

> 状态：已确认
> 日期：2026-08-12
> 基线提交：`4ed5cbd`

## 目标

在保留现有烟柳镇 Demo 和已经完成的交互、战斗、存档、菜单基础上，建立一条可以持续扩展的主流程：先交付烟柳镇完整任务纵向切片，再补落渊村序章和天枢城后续内容。

首个产品目标是让玩家能够从主菜单开始游戏，在烟柳镇完成连续主线任务，经历对话、探索、收集、战斗、任务提交和奖励，并能在任意任务阶段保存与继续游戏。

## 设计依据

- `docs/02-story-design.md` 定义五幕主线：落渊惊变、天枢风云、六镇烽烟、棋局天下、渊海长歌。
- `Assets/Resources/Quests/quest_database.md` 定义烟柳镇 `M01_01` 至 `M01_05`，随后前往天枢城。
- 当前新游戏直接进入 `Demo_YanLiuTown`，场景已有掌柜、苏婉清、钓鱼翁、山贼、头目战斗触发器和南北出口。
- 基线已经支持主菜单、K/E 交互、对话、战斗、背包、装备、武学、v2 存档和 Unity 自动测试。

## 已解决的叙事冲突

当前烟柳镇不再与第二幕的“漕运风云”视为同一段剧情。

统一后的章节顺序为：

```text
落渊惊变（序章，后续制作）
  → 烟柳初行（M01，当前纵向切片）
  → 天枢风云（M02，后续区域）
  → 六镇烽烟
  → 重返烟柳镇（第二幕漕运线，使用新的任务 ID）
  → 棋局天下
  → 渊海长歌
```

`M01_01` 至 `M01_05` 保持现有 ID 和“进京前旅途章”的定位。第二幕重返烟柳镇时使用 `A02_YL_*` ID，不复用 M01 任务或完成状态。

现阶段默认主角名继续使用“凌霜”，角色创建和自定义姓名不属于本路线图前两个阶段。项目继续使用 Unity 6 内置 2D 渲染，不迁移 URP；美术指南中的 URP 建议属于早期设想，不是当前技术约束。

## 方案选择

### 采用：烟柳镇桥接章节

保留现有场景和任务表，把烟柳镇做成序章后、进京前的第一个可玩区域。它能以最低返工成本验证任务、对话、战斗、奖励、存档和章节出口的完整数据流。

### 未采用：严格按剧情总纲先制作落渊村和天枢城

该方案叙事顺序最直接，但需要同时新增至少两个场景、过场资源和大量 NPC，任务基础仍未验证，交付风险过高。

### 未采用：继续把烟柳镇当非剧情系统沙盒

该方案可以快速增加系统，但玩家不会获得明确目标和章节结尾，后续系统也缺少真实内容验证，因此不再继续扩张无主线的 Demo。

## 总体开发阶段

每个阶段单独建立规格和实施计划，完成测试、代码审查和 Unity Play QA 后才能进入下一阶段。

### 阶段一：任务运行时与持久化闭环

建立所有章节共用的任务基础设施。

主要交付：

- `QuestDatabase` 通过稳定 ID 提供正式任务模板，`AcceptQuestById` 不再创建空任务。
- 活跃任务保存独立的运行时目标进度，不修改共享任务模板。
- 统一处理 `TalkToNPC`、`ReachArea`、`CollectItem`、`KillEnemy`、`DefeatBoss` 和 `LearnSkill` 目标事件。
- `QuestGiver` 独立处理可接取、进行中、可提交和完成后的 NPC 行为，不把任务状态继续堆进 `NPCBase`。
- 存档升级为 v3，保存活跃任务、每项目标进度、接取时间和任务状态，并兼容读取 v2 存档。
- 任务奖励只发放一次；物品、金钱、经验和武学奖励均走真实系统入口。
- 无效任务 ID、未知目标、损坏进度和缺失模板只跳过对应数据并报告清晰警告，不破坏其余存档。

验收标准：

1. 通过任务 ID 接取后得到完整名称、描述、目标和奖励。
2. 所有目标类型能够由现有游戏事件推进，且不会重复计数已完成目标。
3. 保存和读取后，活跃任务及目标数值逐项一致。
4. v2 存档仍可读取，缺少活跃任务数据时以空列表恢复。
5. 完成任务只发放一次奖励，重复交互不会再次结算。

### 阶段二：烟柳镇 M01 完整纵向切片

把任务表中的五个主线任务接入现有烟柳镇场景。

主线内容：

1. `M01_01 初到烟柳镇`：进入客栈区域、与掌柜和疯老头交谈。
2. `M01_02 柳家药铺`：找到苏婉清并收集三份疗伤草。
3. `M01_03 玉佩之谜`：找到陈先生、取得废弃书塾古书并返回解读。
4. `M01_04 北山山贼`：进入北山、击败五名山贼和头目黑风。
5. `M01_05 暗流涌动`：向苏婉清告别、向掌柜问路并从南门离开。

场景生成器负责创建缺失 NPC、稳定持久化 ID、任务区域、采集物、古书、山贼和章节出口；重新生成场景与运行时补全都必须幂等，不能产生重复对象。

天枢城尚未制作时，南门出口进入明确的章节结束/预览状态，不加载不存在的场景。完成 `M01_05` 后保存章节完成标志，并允许返回主菜单后继续游戏。

验收标准：

1. 新游戏可以连续完成 M01 五个任务，无需 Inspector 手工配置。
2. Q 任务日志能看到正确任务、目标进度和可提交状态。
3. 中途保存、返回主菜单和继续游戏后，从相同任务阶段继续。
4. 已拾取的唯一任务物、已完成的一次性事件和已击败的头目不会因读档重复出现。
5. 章节结束时给出明确反馈，并保存前往天枢城的解锁状态。

### 阶段三：任务体验与首条支线

补齐任务日志的运行时默认界面、HUD 当前目标、NPC 状态标识、任务接取/更新/完成提示和对应音效入口。实现 `S01_02 柳堤钓鱼翁`，验证重复对话、昼夜条件和武学奖励。

验收标准是：玩家不查看 Console 也能判断下一步目标、可提交 NPC 和获得的奖励；主线与支线可以同时存在并独立保存。

### 阶段四：落渊村序章与跨场景流程

制作落渊村序章，完成村庄遇袭、密信、玉佩、基础移动/战斗/交互教学，并串联：

```text
主菜单 → 落渊村 → 烟柳镇 → 天枢城预览
```

新游戏进入落渊村；开发者直接 Play 烟柳镇时仍保留可测试的独立初始化入口。跨场景位置、任务、世界标志和一次性事件必须正确恢复。

### 阶段五：内容与表现收口

为纵向切片补正式 Animator Controller、核心动画、主要 NPC/敌人美术、基础 BGM/SFX、任务奖励展示和章节结束画面。该阶段不扩建天枢城完整区域，以烟柳镇纵向切片达到稳定可演示质量为结束条件。

## 阶段一架构边界

阶段一只建设任务闭环，不同时实现完整世界模拟、声望、同伴、编年史、商店 UI、天枢城或第二幕内容。

### 任务模板

任务模板由 `QuestDatabase` 按 ID 提供。代码预置表是烟柳镇阶段的可靠基线，`Resources/Quests` 中同 ID 的 `QuestData` 可在未来覆盖代码模板。该模式与现有 `ItemDatabase` 保持一致。

模板中的 `QuestObjective` 只能作为初始定义。接受任务时必须深复制目标列表，运行时进度不得写回模板或其他存档槽位。

### 任务实例

`ActiveQuest` 持有任务 ID、运行时目标、状态和接取时间。显示数据通过任务 ID 解析模板；存档只保存稳定 ID 和运行状态，不序列化 Unity 对象引用。

### 目标事件

现有系统在真实行为发生后调用 `QuestManager.UpdateObjective`：

- `NPCBase`/`QuestGiver` 成功结束指定交互时推进对话目标。
- `AreaTrigger` 首次满足指定区域条件时推进到达目标。
- `ItemPickup` 成功加入背包后推进收集目标。
- 敌人死亡时由独立任务目标组件推进普通击杀或 Boss 目标。
- `MartialArtsSystem.LearnSkill` 首次学会武学后推进学习目标。

失败的拾取、重复学习、无效交互或已完成目标不得产生进度。

### 任务发布与提交

`QuestGiver` 依赖 `NPCBase` 和 `QuestManager`，但不负责显示 UI 或直接发奖励。它根据任务状态选择对话，并在对话结束后的确定时机接取或提交任务。任务奖励统一由 `QuestManager.CompleteQuest` 结算。

### 存档与世界状态

v3 存档增加活跃任务数组和最小世界状态集合。阶段二需要持久化的世界状态包括：唯一拾取物、一次性事件、唯一敌人/Boss 和区域/章节标志。每个持久对象使用稳定 ID；场景加载后根据世界状态决定保留、隐藏或销毁。

存档迁移只向前兼容：v2 读取为空活跃任务和空世界状态；v3 写入后不保证旧版代码能够读取。加载未知任务模板时跳过该任务并记录警告，不能创建空壳任务。

## 核心数据流

```text
NPC 对话结束
  → QuestGiver 接取 M01_01
  → QuestDatabase 解析模板
  → ActiveQuest 深复制目标
  → QuestManager 发布接取事件
  → QuestUI/HUD 刷新

玩家交谈、到达、拾取或击杀
  → 对应行为确认成功
  → QuestManager.UpdateObjective(type, targetId, amount)
  → 目标完成 / 任务变为 Completable
  → QuestUI/HUD 刷新

玩家回到提交 NPC
  → QuestGiver 请求 CompleteQuest
  → QuestManager 校验状态并一次性发奖
  → 写入完成任务与解锁标志
  → 开放下一任务
```

## 测试与交付门槛

每个实施任务采用测试先行，优先在 EditMode 验证任务模板、深复制、目标推进、奖励幂等、存档迁移和世界状态恢复；PlayMode 验证真实 MonoBehaviour 事件链。

每阶段交付前必须完成：

1. 新增回归测试与现有 21 个 EditMode、1 个 PlayMode 测试全部通过。
2. Unity 批处理编译无 C# error/warning。
3. `git diff --check` 通过，场景资源和 `.meta` 完整。
4. 从主菜单执行人工 Play 流程，并验证中途保存、返回菜单、继续游戏。
5. 相对阶段起点执行代码审查，修复所有高优先级问题。
6. 更新 `AGENTS.md`、`README.md` 和 `SETUP_GUIDE.md` 中的长期事实、测试数和已知限制。

## 非目标

- 本路线图前两个阶段不制作完整天枢城、六镇、同伴系统或多结局。
- 不迁移到 URP，不引入新的第三方运行时依赖。
- 不在任务系统中同时实现声望、好感度、编年史和历史问答。
- 不以美术替换阻塞任务闭环；占位资源可以继续用于功能验收。
- 不重写已经稳定的背包、武学和 v2 基础存档，只通过明确接口扩展到 v3。

## 完成定义

路线图的第一个可玩里程碑完成时，玩家能够从主菜单开始，在烟柳镇完成 M01 全部主线，经历探索、对话、收集、战斗、提交和奖励，并在任意任务阶段保存、退出和继续。Console 不出现运行时错误，自动测试与 Unity 人工 QA 均通过。
