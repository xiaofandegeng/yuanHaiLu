# 渊海录：角色与场景美术重建设计

> 状态：已获方向确认，待用户审阅本文后进入实施计划。
>
> 日期：2026-08-14
>
> 分支基线：`main`（开发分支 `codex/art-production-rebuild`）

## 1. 目标与不可变约束

本轮目标是把现有“生成器可产出资源”提升为可辨识、可游玩、可复现的正式像素美术：完成 97 个角色的可读造型，10 个户外和 13 个室内的独立构图，以及序章村庄 normal/burned 两种环境状态。

确定的视觉方向为“叙事像素武侠”：克制的墨色轮廓、自然低饱和区域色、暖色交互焦点、江湖生活细节。角色采用 4 头身的标准像素武侠比例。

以下约束不变：

- 纯 2D；不切换 URP、3D、Unity 版本或内部相机体系。
- 内部渲染 `480×270`；Tile `16×16`；正式角色帧统一 `32×32`；PPU `16`；Point filter、无压缩。
- 户外场景维持 `40×24`，不以扩大画布掩盖构图问题。
- `main` 是唯一合并目标；此前未通过审查的外部美术分支不可直接合并。
- 所有最终资源都必须是提交到仓库的持久 PNG、JSON、Tile、Prefab、Controller 与 Scene；正式运行路径禁止创建 Texture2D/Sprite 色块回退。
- 资源源文件缺失必须让构建失败；不得以已烘焙输出存在来掩盖不可重建的源资产。

## 2. 角色生产设计

角色按“剪影优先、职业其次、地区与身份最后”的层级生产。每个角色至少由发型/头饰、身体轮廓、服装层次、武器或职业道具、配饰、主辅色六个可见设计要素构成；这些要素必须在 1× 游戏尺寸下仍能区分，而不是仅替换调色板。

六职业的固定视觉语义如下：

| 职业 | 剪影与道具 | 主色方向 |
|---|---|---|
| 剑客 | 瘦直轮廓、长剑、长衣摆 | 白/蓝 |
| 拳师 | 宽肩、短衣、拳套或缠手 | 红/橙/墨 |
| 暗器 | 短斗篷、腰包、飞镖 | 黑/紫 |
| 医者 | 药箱、药葫芦、长袖 | 绿/白 |
| 书生 | 书卷、笔、方巾 | 棕/黄/青灰 |
| 异人 | 符箓、罗盘、纹样袍服 | 紫/金 |

97 个角色在第一生产阶段均具备独立可读造型与四方向 `idle`/`walk`、`hurt`、`death`。第二阶段为实际战斗主体补齐动作：12 位主角、24 位敌人、10 位 Boss 完成 `dash`、三段攻击和两类技能；Named/NPC 的动作根据其玩法身份补齐，不能用静态首帧替代已声明的动作。

生成式图像只用于概念参考、服装轮廓和区域色彩提案。进入项目的角色源资产必须重新整理为精确像素网格和可审核模块；每个模块的来源、尺寸、哈希和切片信息由现有流水线记录。

## 3. 环境生产设计

每个正式场景的布局 JSON 是唯一结构来源。`Ground`、`Water`、`Lower Environment`、`Buildings`、`Foreground`、`Effects`、`collisions`、`anchors` 都必须显式声明；生成器只解析这些声明，不得再绘制固定中央道路、对称房屋或公式化装饰。

每个户外区域至少具有：一条主路线、一条可选支路、三处区域专属地标、可读的前景遮挡、与建筑/地形一致的碰撞，以及独立的几何坐标签名。区域构图原则如下：

| 区域 | 视觉骨架 |
|---|---|
| 天枢 | 市井主街、官署侧院、飞檐与暗巷 |
| 苍岳 | 曲折崖道、松林、石阶与寺院 |
| 烟柳 | 河网、石桥、船泊位、柳堤临河屋 |
| 赤砂 | 沙丘斜线、关隘、烽火台、驿站 |
| 幽篁 | 竹林迷径、溪流、机关空地与雾口 |
| 寒渊 | 雪脊、冰裂、温泉、古墓入口 |
| 序章村庄 | 民居环路、晒谷场、村口与火灾后废墟 |
| 落渊 | 旧城街巷、遗迹、水岸与市场残片 |
| 绝云 | 剑派山门、台阶、栈道、云崖 |
| 镇岳 | 祭坛轴线、碑林、山道、观景台 |

13 个室内不使用同一房间模板：客栈有柜台/桌席/后厨，药铺有药柜/诊席，书院有桌案/书架，衙门有公案/牢门，船舱有货物/舷窗，其他室内同样用其功能物件、动线与遮挡区分。

序章村庄 `normal` 与 `burned` 保持同一 scene ID、尺寸、入口、锚点与碰撞。`burned` 仅替换 Tile/Sprite/地标和天气表现，使用炭化墙屋、破损植被、余烬与烧毁物，确保剧情切换不破坏导航和存档。

## 4. 生产流程与质量门

1. 先补齐和验证所有角色源模块，修复编译阻塞；源资产检查必须在烘焙前完成。
2. 为角色建立可见差异清单和精确切片，先产出角色图集/Pivot/动画命名，再生成 Prefab 与 Controller。
3. 逐区域补全显式布局，删除公式化绘制，重建 23 个正式 Scene 和碰撞。
4. 加入序章状态变体，验证状态切换不改变锚点与碰撞。
5. 用 Unity 生成的临时截图做人工视觉检查；人工通过后才更新仓库基线。
6. 运行 Python 全量流水线、Unity EditMode、PlayMode、场景重建确定性检查和可见窗口主流程 QA。

完成条件不是文件数量，而是同时满足：资源可从干净检出重建；97 个角色在游戏尺寸可分辨；十个户外场景的几何结构不同；23 个场景由布局完整驱动；序章可切换两种状态；自动与人工验证均有真实证据。

## 5. 失败处理与交付

任何缺失源文件、未解析 token、编译错误、布局同构、截图未审批、许可证导致 Unity 测试未跑，都会阻止合并。修复必须在同一开发分支追加提交，并从受影响阶段重新验证。

最终交付将记录：分支与基线哈希、资源统计、Python/Unity 测试 XML 与日志、十一张视觉截图、人工 Play QA 结果、已知风险。所有 P0/P1 清零并获得用户合并授权后，才合并到 `main`。
